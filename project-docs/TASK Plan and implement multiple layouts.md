TASK: Plan and implement multiple layouts from one input pattern,
grouped by textile type, in SeamlyLayout.

GOAL

Allow SeamlyLayout to receive one SVG containing pieces for multiple textile
types, separate those pieces by textile type, configure media independently
for each textile type, create one layout per textile type, adjust those
layouts independently, and export all resulting layouts together.

IMPORTANT:
Do not begin implementation immediately.

PHASE 1 is architecture analysis and planning only.

Present the implementation plan to me and STOP for discussion.

After I explicitly approve the plan, implement the approved plan without
asking for permission at each implementation step unless a material
architectural issue requires changing the approved design.

================================================================
1. ANALYZE CURRENT IMPLEMENTATION
================================================================

Before proposing changes, inspect the existing SeamlyLayout implementation
and identify:

1. How the input stringified SVG is received, stored, parsed, and displayed.

2. How piece metadata and SVG data-* attributes are currently parsed.

3. How Settings is implemented.

4. How media settings are currently represented, including:
       - fabric
       - paper
       - dimensions
       - margins
       - units
       - folded/single fabric handling

5. How Create Layout calls process_layout().

6. Whether process_layout() is stateful or can safely be called multiple
   times for independent inputs.

7. How input SVG state and layout state are stored.

8. How Adjust Mode operates on the current layout.

9. How Export operates and how filenames are generated.

10. How the left input canvas and right layout canvas are implemented.

11. Existing tab-control patterns, if any.

12. Existing tests covering:
       - SVG parsing
       - media settings
       - layout generation
       - adjustment
       - export

Document the principal files/classes/functions that would be affected.

================================================================
2. TEXTILE TYPE SOURCE
================================================================

Use textile classification metadata embedded in the input SVG.

The expected metadata comes from Seamly2D.

At minimum, inspect:

    data-piece-type
    data-textile-type

The grouping key for this feature should normally be:

    data-textile-type

for pieces where:

    data-piece-type="textile"

Expected textile types may include:

    shell
    lining
    interfacing
    interlining
    padding_insulation
    reinforcement
    other

Do not assume these exact values without first inspecting the actual SVG
generated by Seamly2D.

Use stable machine-readable identifiers internally.

Use translated human-readable labels in the UI.

Example:

    shell -> Shell / Main Fabric
    lining -> Lining
    interfacing -> Interfacing

Do not group pieces by translated display text.

================================================================
3. MISSING OR UNKNOWN METADATA
================================================================

Define explicit behavior for pieces that:

    - have no data-piece-type
    - have no data-textile-type
    - have an unknown textile type

For backward compatibility, pieces without classification metadata should
normally be treated as:

    pieceType = textile
    textileType = shell

unless inspection of existing SeamlyLayout behavior indicates a safer
compatibility rule.

Unknown future values must not cause the SVG to fail to load.

Unknown values should be retained and displayed with an appropriate fallback
label.

================================================================
4. SETTINGS: SEPARATE BY TEXTILE TYPE
================================================================

Add a Settings option:

    [ ] Create separate layouts by textile type

When unchecked:

    preserve existing SeamlyLayout behavior exactly.

When checked:

    identify the unique textile types present in the current input SVG.

Do not create duplicate entries for multiple pieces of the same textile type.

================================================================
5. PER-TEXTILE MEDIA SETTINGS
================================================================

For every unique textile type, provide independent media settings.

Create an explicit per-textile configuration model rather than storing these
values only as transient widget state.

Conceptually:

    TextileLayoutSettings
        textileType
        mediaType
        fabricConfiguration
        paperType
        width
        height
        margins
        other applicable media settings

Use the project's existing media-setting structures where possible rather
than duplicating them.

------------------------------------------------------------
FABRIC
------------------------------------------------------------

If media type is Fabric, support the existing applicable fabric settings.

At minimum:

    configuration:
        single
        folded

    left margin
    top margin
    right margin
    bottom margin

If folded fabric has special geometric rules, use the existing SeamlyLayout
media model.

Do not simply hard-code:

    leftMargin = 0

unless that matches the current folded-fabric implementation.

Clearly define how usable width is calculated for folded fabric.

------------------------------------------------------------
PAPER
------------------------------------------------------------

If media type is Paper, support existing paper settings.

At minimum:

    paper type / size
    orientation if currently supported
    left margin
    top margin
    right margin
    bottom margin

Use existing paper definitions and units.

Do not create a second independent paper-size implementation.

================================================================
6. SETTINGS UI
================================================================

When "Create separate layouts by textile type" is enabled:

display one configuration section per textile type discovered in the SVG.

The UI should clearly associate each media configuration with its textile
type.

Recommend an appropriate UI during planning, for example:

    tabs
    stacked pages
    expandable sections
    table + details panel

Prefer whichever pattern best matches the current SeamlyLayout UI.

Do not assume that tabs are necessarily the best choice inside Settings.

================================================================
7. APPLY BEHAVIOR
================================================================

When the user selects Apply:

1. preserve the original source SVG unchanged;

2. derive one filtered SVG document/string for each textile type;

3. each filtered SVG must contain only pieces belonging to that textile type;

4. retain SVG document metadata required for SeamlyLayout processing;

5. retain relevant per-piece metadata and identifiers;

6. store the filtered SVGs in an internal collection keyed by the stable
   textile-type identifier.

Conceptually:

    textileInputs["shell"]
    textileInputs["lining"]
    textileInputs["interfacing"]

Do not repeatedly parse and mutate the original SVG if a cleaner parsed
representation exists.

Determine the safest architecture during Phase 1.

================================================================
8. INPUT CANVAS
================================================================

When textile separation is enabled:

display tabs across the top of the left input canvas.

Each tab represents one textile type.

Example:

    [Shell / Main Fabric] [Lining] [Interfacing]

Selecting a tab displays only that textile type's input pieces.

Use the human-readable translated textile label for the tab.

Internally use the stable textile identifier.

Preferred ordering:

1. shell / main fabric
2. lining
3. interfacing
4. interlining
5. padding / insulation
6. reinforcement
7. other / unknown

If a type is absent, do not create an empty tab.

Do not label the first tab "Fabric" unless the actual classification being
displayed is Fabric.

If only one textile type exists, determine during planning whether the tab
bar should remain visible or be hidden.

================================================================
9. CREATE LAYOUT
================================================================

When textile separation is enabled:

Create Layout must independently run layout generation for each textile
input.

Conceptually:

    for textileType in textileInputs:
        result = process_layout(
            textileInputs[textileType],
            mediaSettings[textileType]
        )

Store each result independently.

Conceptually:

    textileLayouts["shell"]
    textileLayouts["lining"]
    textileLayouts["interfacing"]

Do not combine geometry from different textile types into the same layout.

Use each textile type's own media configuration.

Determine whether process_layout() can safely be called successively using
the current architecture or whether isolated processing state is required.

================================================================
10. ERROR HANDLING DURING MULTIPLE LAYOUTS
================================================================

Define behavior when one layout fails.

Preferred behavior:

    - attempt all textile types;
    - retain layouts that succeed;
    - clearly report which textile types failed;
    - do not silently discard successful layouts.

Do not leave the application in a partially corrupted state.

If process_layout() currently makes all-or-nothing assumptions, document the
required architectural change in the Phase 1 plan.

================================================================
11. LAYOUT CANVAS
================================================================

When separate layouts have been generated:

display textile-type tabs across the top of the right layout canvas.

Example:

    [Shell / Main Fabric] [Lining] [Interfacing]

Selecting a tab displays the corresponding generated layout.

Use the same tab ordering as the input canvas.

Where practical, switching the input tab should also select the corresponding
layout tab, and vice versa.

Evaluate this behavior during planning.

================================================================
12. ADJUST MODE
================================================================

Adjust Mode operates only on the currently selected textile layout.

Adjustments made to one textile layout must not modify another textile
layout.

Switching tabs must preserve each layout's adjustment state.

Example:

    adjust Shell layout
    switch to Lining
    adjust Lining layout
    switch back to Shell

The previous Shell adjustments must still be present.

Document how this state will be stored.

================================================================
13. EXPORT
================================================================

When textile separation is disabled:

preserve current Export behavior.

When textile separation is enabled:

Export should export ALL successfully generated textile layouts.

Create one export result per textile type using the currently selected export
format(s).

Use stable and collision-safe filenames.

Propose a naming convention during Phase 1.

Preferred conceptual naming:

    <pattern-name>-shell.<ext>
    <pattern-name>-lining.<ext>
    <pattern-name>-interfacing.<ext>

Use identifiers suitable for filenames rather than translated UI labels.

If multiple files are produced, package them into:

    <pattern-name>-layouts.zip

Do not create unnecessary nested directories unless they improve existing
export behavior.

The ZIP should contain only successfully exported files.

If one export fails:

    report the failed textile type;
    preserve successfully exported files where practical;
    do not silently report complete success.

================================================================
14. STATE MANAGEMENT
================================================================

The plan must explicitly define ownership of:

    original SVG
    parsed SVG data
    textile-type list
    filtered textile SVG inputs
    per-textile media settings
    generated layouts
    per-layout adjustment state
    active textile tab

Avoid using parallel unrelated arrays indexed only by position.

Prefer a keyed structure based on stable textile-type identifiers.

Example concept:

    TextileLayoutJob {
        textileType
        displayName
        filteredSvg
        mediaSettings
        layoutResult
        adjustmentState
        status
    }

This is conceptual only.

Use naming and types consistent with the existing Rust/iced SeamlyLayout
architecture.

================================================================
15. APPLICATION STATE CHANGES
================================================================

Define what happens when:

A. A new SVG is loaded.
B. Textile separation is turned on.
C. Textile separation is turned off.
D. Apply is clicked again.
E. Media settings for one textile type change.
F. Create Layout is run a second time.
G. The SVG contains a different set of textile types.
H. A layout has already been adjusted when settings change.

The implementation must not retain stale layouts or stale settings
incorrectly.

Preserve reusable settings where reasonable, but clearly invalidate derived
layout results when their input or media configuration changes.

================================================================
16. PERSISTENCE
================================================================

During Phase 1, determine whether per-textile media settings should:

    - apply only to the current job, or
    - persist in SeamlyLayout Settings.

Do not introduce persistent storage without considering compatibility with
the existing Settings model.

The global option:

    Create separate layouts by textile type

may be persisted if that is consistent with existing SeamlyLayout settings.

================================================================
17. EXTENSIBILITY
================================================================

Do not hard-code logic that only works for:

    shell
    lining
    interfacing

Future textile types must be able to pass through the grouping and layout
pipeline without architectural changes.

Known types may have preferred ordering and translated labels, but unknown
types must still be supported.

The eventual system may also process Trim Materials separately.

Do not implement trim-material layout separation in this task unless required
for architectural consistency.

However, avoid an implementation that would prevent future grouping by:

    data-trim-material-type

or other classification dimensions.

================================================================
18. TESTING
================================================================

The implementation plan must include tests for at least:

1. SVG containing only Shell pieces.

2. SVG containing Shell + Lining pieces.

3. SVG containing Shell + Lining + Interfacing pieces.

4. Repeated pieces of the same textile type producing only one textile group.

5. Legacy SVG without textile metadata.

6. Unknown textile type.

7. Separation disabled preserves current behavior.

8. Separate per-textile media settings.

9. Fabric single configuration.

10. Fabric folded configuration.

11. Paper media configuration.

12. Correct filtering of SVG pieces by textile type.

13. Independent calls to process_layout().

14. Independent layout state.

15. Adjust Mode affecting only the active layout.

16. Adjustment state surviving tab switches.

17. Export of multiple layouts.

18. Correct ZIP contents and filenames.

19. One layout failing while another succeeds.

20. Loading a new input invalidating obsolete textile/layout state.

Use current SeamlyLayout test conventions where possible.
