## Overview

The `cxxqt_bridge` crate (at `crates/cxxqt_bridge/`) is the boundary between the
Qt 6.10 + QML frontend (LGPL-3.0) and the Rust core crates (MIT).

CXX-Qt automatically generates C++ glue code from Rust macros — no manual
`extern "C"` declarations or cbindgen needed.

```
Qt/QML frontend
      │
      │  C++ (auto-generated by CXX-Qt)
      ▼
cxxqt_bridge  ◄──  #[cxx_qt::bridge] macros in src/lib.rs
      │
      │  Rust function calls
      ▼
geometry, svg_dom, app_core, layout_engine, seamly_svg2ezdxf, ezdxf2dxfastm
```

## Key Macros (Phase 2b–2e)

| Macro | Purpose |
|-------|---------|
| `#[cxx_qt::bridge]` | Marks a Rust module as a bridge; triggers C++ code generation |
| `#[qobject]` | Makes a Rust struct a Qt QObject subclass |
| `#[auto_cxx_name]` | On `extern "RustQt"` block: converts all snake_case Rust names to camelCase for C++/QML. Required so QML can use `onErrorOccurred` instead of `onError_occurred`. |
| `#[qproperty]` | Declares a Qt property with auto-generated getter/setter/signal |
| `#[qsignal]` | Declares a Qt signal callable from QML |
| `#[qinvokable]` | Exposes a Rust method as a Q_INVOKABLE callable from QML |

**Not used:** `#[qml_element]` — Do not use this macro. `qmltyperegistrar` cannot follow CXX-Qt's
`rust/cxx.h` template include chain, producing "AppController cannot be found" warnings without
actual registration. Use `qmlRegisterType` at runtime instead (see QML Registration below).

## CMake Integration (Phase 2f)

`cxx_qt_import_crate` is provided by a **separate** cmake-only repository:
`https://github.com/kdab/cxx-qt-cmake.git`. It is a wrapper over Corrosion's
`corrosion_import_crate` that compiles the Rust crate via Cargo and creates a
linkable CMake target.

**Important:** The main CXX-Qt source repo (`https://github.com/KDAB/cxx-qt.git`)
does NOT contain the cmake integration functions. Its `cmake/` directory only
contains `CompilerCaching.cmake`. Always fetch from `cxx-qt-cmake` for cmake
integration.

```cmake
include(FetchContent)
FetchContent_Declare(
    CxxQt
    GIT_REPOSITORY https://github.com/kdab/cxx-qt-cmake.git
    GIT_TAG        main
)
FetchContent_MakeAvailable(CxxQt)

cxx_qt_import_crate(
    MANIFEST_PATH "${CMAKE_SOURCE_DIR}/../Cargo.toml"
    CRATES        cxxqt_bridge
    QT_MODULES    Qt::Core Qt::Qml
)
```

**Windows/MSVC note:** Set `CMAKE_MSVC_RUNTIME_LIBRARY "MultiThreadedDLL"` before
any targets to match Rust's non-debug DLL runtime and avoid LNK2038 errors.

## Memory Ownership

- Rust owns all data; Qt/QML holds references via the QObject wrapper.
- CXX-Qt enforces ownership rules at compile time through the bridge types.
- `#[qproperty]` fields are owned by the Rust struct; Qt reads/writes via
  generated C++ accessors.
- Signals are emitted from Rust; Qt connects slots on the C++ side.

## QML Type Registration (Phase 2f)

**The correct approach: `qmlRegisterType` at runtime in `main.cpp`.**

CXX-Qt's staticlib crates compile moc output for `AppController` into the `.lib`. Adding the
generated header to cmake SOURCES causes AUTOMOC to generate a duplicate moc → LNK2005.
The `QML_FOREIGN` shim approach fails because `qmltyperegistrar` cannot resolve `AppController`
through CXX-Qt's `rust/cxx.h` template include chain.

**Solution:**
```cpp
// main.cpp — include ONLY from here; do NOT add to cmake SOURCES
#include <cxxqt_bridge/src/lib.cxxqt.h>

// Before creating QQmlApplicationEngine:
qmlRegisterType<AppController>("SeamlyLayout", 1, 0, "AppController");
```

This registration happens at runtime before `engine.loadFromModule()`, so QML resolves
`AppController` correctly via the "SeamlyLayout" URI.

## Crate Edition Note

The `cxxqt_bridge` crate **must** use `edition = "2021"` in its `Cargo.toml`.
`cxx-qt-build 0.7.3` is not compatible with Rust edition 2024. Using `"2024"` causes
build errors in the generated C++ glue code.
